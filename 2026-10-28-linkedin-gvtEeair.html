01. Najważniejsza zmiana: liczy się ukończona praca, nie ilość kodu

Jay Parikh w artykule opublikowanym 28 października 2026 r. przedstawia kierunek rozwoju GitHuba: od narzędzi wspierających pojedynczego programistę do systemu, w którym człowiek wyznacza cel, podejmuje decyzje i odpowiada za rezultat, a agenci AI wykonują i weryfikują część pracy.

Główna teza

Jednostką wartości w software engineering ma być dostarczona funkcjonalność, naprawiony błąd lub usunięte ryzyko bezpieczeństwa. Sam wygenerowany kod nie jest wystarczającym rezultatem.

GitHub traktuje SDLC jako proces nieliniowy. Pracę może rozpocząć nowe wymaganie, problem produkcyjny, telemetryka lub zmiana w kodzie. Agent może przechodzić między analizą, implementacją, testowaniem i code review, a człowiek zachowuje odpowiedzialność za wdrożenie.

01 / VELOCITY

Szybkość dostarczania

Ograniczenie czasu od pomysłu do zakończonej i zweryfikowanej zmiany.

02 / INTELLIGENCE

Kontekst i uczenie się

Wykorzystanie informacji z platformy i rezultatów wcześniejszych zadań.

03 / QUALITY

Jakość i bezpieczeństwo

Wykrywanie istotnych problemów przed wdrożeniem, także przy wzroście wolumenu kodu.

04 / CONTROL

Kontrola przez zespół

Decyzje, odpowiedzialność, narzędzia i koszty pozostają pod kontrolą użytkowników.

02. Sześć najważniejszych ogłoszeń produktowych

GitHub Copilot App

Jedno środowisko pracy

Aplikacja skoncentrowana na pracy z agentami. Pozwala kierować zadaniami od issue do merge, pracować nad specyfikacjami, analizować telemetrię i prowadzić dyskusje projektowe w jednym interfejsie.

Znaczenie: punkt koordynacji dla człowieka zarządzającego pracą agentów, nie kolejny edytor z autouzupełnianiem.

Copilot Fusion

Router i orkiestrator modeli

System automatycznie dobiera modele oraz sposób ich współpracy do zadania. Może wykorzystać jeden model, kaskadową weryfikację albo równoległą krytykę kilku modeli. Szczegóły poniżej.

Znaczenie: optymalizacja kompromisu koszt, jakość i opóźnienie bez ręcznego przełączania modeli.

Copilot Projects

Public preview

Długotrwały cel projektu może być realizowany w wielu repozytoriach i równoległych sesjach. Użytkownik śledzi postęp, zatwierdza decyzje oraz przekazuje kontekst i materiały z biblioteki projektu. Projekty obsługują również zadania cykliczne.

Znaczenie: zarządzanie strumieniem pracy i rezultatami zamiast ręcznego obsługiwania każdej sesji agenta.

Session Continuity

Sesje w chmurze

Jedna sesja może być kontynuowana na GitHub.com, w Copilot App, CLI, VS Code i na urządzeniach mobilnych. Kontekst i stan pracy pozostają w środowisku chmurowym.

Znaczenie: możliwość uruchamiania, nadzorowania i korygowania pracy bez przywiązania do pojedynczego urządzenia.

Copilot Automations

Zdarzenia i harmonogram

Agenci mogą uruchamiać się według harmonogramu, po zdarzeniach repozytorium albo przez API. Przykładowe scenariusze obejmują triaż zgłoszeń, przygotowanie review i analizę incydentów. Automatyzacje mogą proponować ulepszenia swoich konfiguracji, które człowiek ocenia i zatwierdza.

Znaczenie: krok od asystenta reagującego na prompt do kontrolowanej automatyzacji pracy inżynierskiej.

Copilot Code Review Max

Public preview

Nowy poziom dokładniejszego przeglądu zmian. GitHub udostępnia trzy poziomy intensywności review: Lite, Balanced i Max. Max jest przeznaczony do bardziej złożonych, krytycznych zmian i wykorzystuje wiele modeli o silnych zdolnościach rozumowania.

Znaczenie: skalowanie kontroli jakości wraz ze wzrostem liczby pull requestów generowanych przez AI.

03. Copilot Fusion: ważniejsza staje się orkiestracja modeli

Fusion nie jest pojedynczym modelem LLM. To warstwa wykonawcza, która na podstawie zadania dobiera model lub kilka modeli oraz poziom wysiłku. Dokumentacja opisuje trzy wzorce działania:

WzorzecPrzebiegZastosowanie
SingleJeden model wykonuje zadanie.Proste, dobrze określone problemy.
CascadeTańszy model proponuje rozwiązanie, kontroler akceptuje lub eskaluje do mocniejszego.Zadania wymagające ekonomicznej walidacji.
CritiqueJeden model tworzy odpowiedź, kilka modeli niezależnie ją ocenia, potem następuje poprawa.Problemy wymagające głębszej analizy.

Dostępne są poziomy wysiłku Standard, High i Max. Wersja Standard faworyzuje ekonomię, a Max głębsze rozumowanie. Fusion uwzględnia dostępność modeli, polityki organizacji i ograniczenia kontekstu. Dokumentacja wspomina także eksperymentalną obsługę wybranych modeli lokalnych.

Wynik wydajności podawany przez GitHub

Według ogłoszenia Fusion Max uzyskał rezultat w indeksie Artificial Analysis Coding Agent Index oddalony o mniej niż trzy punkty od Opus 5.5 Max, przy około połowie kosztu i czasie na zadanie krótszym o 40%. To przytoczona deklaracja producenta w określonym benchmarku, a nie gwarancja dla dowolnego projektu.

Uwaga kosztowa: nie ma osobnej opłaty za sam router Fusion, ale naliczane są koszty modeli użytych w danym zadaniu. Poziomy High i Max mogą uruchamiać kilka modeli, a więc nie muszą być tańsze od Standard. W dokumentacji wskazano 30% zniżki na koszty modeli przy używaniu Fusion w płatnych planach do 30 listopada 2026 r.

Dokumentacja: About GitHub Copilot Fusion.

04. AI Code Review: więcej automatyzacji oznacza większą potrzebę kontroli

Wzrost produkcji kodu zwiększa liczbę zmian wymagających weryfikacji. GitHub podkreśla, że przyspieszenie implementacji nie ma wartości, jeżeli równocześnie rośnie liczba defektów trafiających do produkcji.

TrybCharakterŚredni koszt review*
LiteSzybki przegląd typowych błędów i problemów bezpieczeństwa.ok. 0,25 USD
BalancedDokładniejsza analiza skomplikowanej logiki i zmian między usługami.ok. 1,50 USD
MaxNajgłębszy przegląd dla zmian wysokiego ryzyka.ok. 10 USD

* Szacunki ze strony GitHub Docs, nie cennik stały. Zależą od rozmiaru pull requesta i kontekstu repozytorium, nie uwzględniają kosztów GitHub Actions. Max jest w public preview.

GitHub podał, że Max osiągnął najwyższy wynik F1 dla problemów wysokiej wagi w benchmarku ReviewBench. Wynik należy interpretować jako informację o teście, nie dowód, że narzędzie wykryje każdy błąd ani substytut testów i review człowieka.

Interpretacja architektoniczna

W praktyce warto różnicować poziom review według ryzyka: Lite dla zmian rutynowych, Balanced dla złożonych obszarów biznesowych, Max dla krytycznych fragmentów systemu. Uzupełnieniem nadal powinny być testy automatyczne, kontrola architektury, analiza zależności i odpowiedzialność właściciela kodu.

Dokumentacja: GitHub Copilot code review.

05. Dostępność, licencjonowanie i ograniczenia

GitHub wprowadza zmianę dla klientów GitHub Enterprise: dostęp do funkcji Copilot bez potrzeby osobnej subskrypcji Copilot, z rozliczaniem zużytych AI credits. Dostęp przez dział sprzedaży został ogłoszony 28 października 2026 r., a samoobsługowe wdrożenie ma pojawić się później. Istniejący klienci Business i Enterprise mogą zachować dotychczasowe plany lub przejść na nowy sposób rozliczania.

FunkcjaCo należy wiedzieć
FusionDostępny w planach Copilot; konkretne modele i poziomy wysiłku zależą od planu i polityk.
ProjectsW aplikacji Copilot, public preview; cele mogą obejmować wiele repozytoriów.
AutomationsTylko repozytoria prywatne i wewnętrzne; wymagają odpowiedniego planu i aktywnego cloud agenta.
Code ReviewPłatne plany Copilot; poziom Max w public preview; koszty w AI credits i potencjalnie Actions.
EnterpriseNowe rozliczanie według wykorzystanych AI credits, początkowo przez sprzedaż.

Przed wdrożeniem automatyzacji

  • Nadaj agentom tylko niezbędne uprawnienia, w tym uprawnienia do narzędzi MCP.
  • Oddziel tworzenie zmian od akceptacji i wdrażania, szczególnie dla kodu wysokiego ryzyka.
  • Ustal limity AI credits na uruchomienie i okres rozliczeniowy.
  • Pamiętaj, że automatyzacje mogą pobierać opłaty za AI credits oraz minuty GitHub Actions.
  • Traktuj samodoskonalenie automatyzacji jako propozycje zmian wymagające zatwierdzenia, a nie niekontrolowane modyfikacje.

Dokumentacja: Copilot automations oraz Copilot projects.

06. Dlaczego GitHub przebudowuje infrastrukturę?

Praca agentów generuje nowe obciążenie: większą liczbę zmian w repozytoriach, operacji Git, sesji i wywołań narzędzi. GitHub ogłosił inwestycje w moc obliczeniową, pamięć masową i sieć, a także migrację w stronę wdrożenia Azure w wielu regionach, z planowanym zakończeniem na początku 2027 r.

Dodatkowo firma wskazała trzy zasady modernizacji własnej architektury Git:

  1. Uproszczenie prymitywów, czyli redukcja złożoności podstawowych mechanizmów.
  2. Oddzielenie storage od compute, aby skalować zasoby niezależnie.
  3. Minimalizacja koordynacji, aby ograniczać wąskie gardła przy współbieżnej pracy.

To sygnał, że adopcja agentów jest również problemem architektury platformowej, a nie tylko jakości modeli LLM. Oprogramowanie musi obsłużyć nowe wzorce obciążenia oraz większy wolumen operacji wykonywanych automatycznie.

Rozwinięcie: Building Git infrastructure for agent-scale development.

07. Co z tego wynika dla architektów i zespołów IT?

Poniższe punkty są interpretacją i rekomendacjami, a nie zapowiedziami nowych funkcji GitHuba. Artykuł wskazuje kierunek rozwoju AI-native SDLC, ale nie dowodzi automatycznie wzrostu produktywności w każdej organizacji.

ARCHITECTURE

Specyfikacje i granice

Dostarczaj agentom wymagania jakościowe, decyzje architektoniczne, granice modułów oraz kryteria akceptacji. Sam prompt opisujący funkcję zwykle nie wystarczy do utrzymania spójności dużego systemu.

ENGINEERING

Sprawdzalny rezultat

Mierz wykonane zadania, defekty po wdrożeniu, czas od issue do merge, koszt na zmianę i wielkość poprawek. Liczba wygenerowanych linii kodu nie jest miernikiem wartości.

QUALITY

Automatyczne bramki jakości

Połącz testy, statyczną analizę, reguły architektury i AI review. Definiuj warunki, bez spełnienia których agent nie może uznać zadania za zakończone.

OPERATIONS

Human-in-the-loop

Wyznacz miejsca wymagające zatwierdzenia przez człowieka, uprawnienia do zmian, limity kosztów, śledzenie sesji i sposób audytu działań agentów.

Przykładowy pilotaż w zespole

  1. Wybierz jedno repozytorium i kategorię niskiego ryzyka, np. analizę issue albo poprawki testów.
  2. Dodaj do repozytorium instrukcje dla agentów, zasady architektury i obowiązkowe testy.
  3. Porównaj pracę ręczną i agentową na podobnych zadaniach, uwzględniając review, poprawki i koszt.
  4. Dopiero po pomiarach rozszerz automatyzacje na większą liczbę repozytoriów i trudniejsze zmiany.
Podsumowanie

Najistotniejszą zmianą nie jest kolejny model do generowania kodu. GitHub buduje system, w którym agenci mogą przejmować fragmenty procesu dostarczania oprogramowania, a rola zespołu przesuwa się w kierunku definiowania celów, ograniczeń, pomiaru jakości i nadzorowania wykonania.
